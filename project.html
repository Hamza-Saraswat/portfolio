Juju — RAG Slack Assistant

FieldPulse's internal knowledge assistant. Custom RAG pipeline in production, now evolving to MCP-based architecture. 69.2% accuracy, ~30 messages/day, ~30 minutes saved per user per day.

Context

FieldPulse needed a way to surface internal knowledge

FieldPulse is a field service management platform with ~200 employees. Sales, support, and implementation teams were answering the same customer questions daily, searching across Slack history, Notion docs, and internal wikis. Knowledge existed — it was just scattered and unsearchable.

Problem

30+ minutes per user per day lost to knowledge lookup

Teams were spending significant time on repetitive searches. No unified search. No single source of truth. New hires took weeks to become self-sufficient because they couldn't find answers without asking senior teammates.

Approach

Build where teams already work — Slack

Instead of building another tool nobody would adopt, I put the assistant inside Slack where teams already spend their day. The architecture: ingest all internal docs into Supabase PGVector, add Cohere reranking for relevance, orchestrate with n8n, and respond directly in Slack threads.

Architecture

Juju 1.0 to 2.0: Custom RAG to MCP

Juju 1.0 was a custom RAG pipeline: document chunking, PGVector embeddings, Cohere reranking, n8n orchestration. It works. Juju 2.0 is the evolution — moving to MCP-based architecture for better tool use, multi-step reasoning, and easier extensibility. The goal is an assistant that can not just answer questions but take actions.

Retrospective

What I'd do differently

I'd instrument from day one. We added LangWatch evaluation after launch, but having eval pipelines running from the first version would have caught accuracy issues faster. I'd also start with a smaller, curated document set instead of ingesting everything — quality of source docs matters more than quantity for RAG accuracy.
